## Purpose & scope
An MCP connector to each city install (Kharkiv `dovira.vet`, Kyiv `kyiv.dovira.vet` — two connections, two databases) through which the owner, the content manager and the developer manage the site's content from Claude (claude.ai web connector, Claude Desktop) in natural language: read every post type, change prices, add pages and blog posts (Kharkiv only), upload images, create and edit blog categories and tags. Every connector user is a real WP user connecting with their own application password; administrators and editors have the same content scope, and only administrators may delete (to the WordPress trash). Every write, in every language, is previewed and happens only with a confirmation token the preview issued; inside the first confirmed write of a session the connector dumps the database into a web-closed folder — a new timestamped file every time. The Russian copy of a changed Ukrainian post is updated in the same session under the same rule.
OUT of scope: site settings (WP options, the ACF options page «Налаштування»), users, plugins, themes; writing to `conversation`, `application`, `questionary` (read-only — status stays with the admin and Dovira Bridge); permanent deletion; roll-back as a connector action; one connector for both cities; a Kyiv blog; translating on the server.

## Fit into the host
- **Code location:** `wp-content/themes/dovira/inc/features/content-mcp/` (namespace `dovira\ContentMcp`; tests in `tests/Unit/ContentMcp/`); the plugin `wp-content/plugins/mcp-adapter/` (third-party, committed) is its transport
- **Host area:** theme `dovira` — obeys its `CLAUDE.md` isolation rules
- **Entry point:** `inc/features/content-mcp/bootstrap.php`, required by one plain line in `functions.php`; it returns at once (the site loads as before) unless `wp_register_ability()` and the adapter's `WP\MCP\Core\McpAdapter` exist, then registers the ability category `dovira` on `wp_abilities_api_categories_init` (core refuses an ability whose category is not registered first), the abilities on `wp_abilities_api_init` and the server on `mcp_adapter_init` (the adapter fires it on `rest_api_init` priority 15, on `init` priority 20 under WP-CLI). The names the server lists and the names registered are one constant, `Catalogue::TOOLS`; every ability carries `meta.mcp.public: false`, so the adapter's default server neither discovers nor executes it, and `meta.show_in_rest: true` for REST `wp-abilities/v1`
- **Session:** the adapter gives an ability only its input, so `Session` reads the `Mcp-Session-Id` header from the REST request of `/mcp/dovira` (`rest_request_before_callbacks`); any other request has the session `''`
- **Shared code it depends on:** the registered post types (`inc/post-types/*.php`) and taxonomy; the ACF local field groups and block definitions (`inc/acf/**`) it introspects — read only, never changed by this feature; Polylang (`pll_get_post`, `pll_set_post_language`, `pll_save_post_translations`); `wp-config.php` constant `DOVIRA_MCP_DUMP_DIR`

## Data
Owns no table and no post type. Owns: the transients `dovira_mcp_confirm_{hash}` (a pending confirmation: user, session, payload hash; 15 min) and `dovira_mcp_dumped_{session}` (24 h); the dump files `dovira-{host}-{YYYY-MM-DD}-{HHMMSS}.sql.gz` in `DOVIRA_MCP_DUMP_DIR` (fallback `wp-content/backup-db/`, with the `.htaccess` and `index.php` it writes there); the daily cron hook `dovira_mcp_dump_retention` and the filter `dovira_mcp_dump_retention_days` (default 90); the server's sessions are the adapter's (user meta). It writes posts, postmeta (through ACF), terms and attachments that belong to `core` — as the connected user, through the same functions the admin uses (details in `docs/DATA-MODEL.md` → Feature `content-mcp`).

## Invariants
- No write without a valid confirmation token for this payload, user and session; a read never issues one.
- No write before the session's dump exists; a failed dump aborts the write with an error. A dump file is never overwritten or renamed.
- The server exposes only `dovira/*` abilities; no write ability exists for `conversation`, `application`, `questionary`; `service-city` terms and the options page are never written; `trash-post` requires `manage_options`.
- ACF values go through `update_field()`, never raw postmeta; an existing service's price rows are changed only by `update-price-row`, which never changes `is_price_general` or the `cities` checklist; a new service's rows are written by `create-post` as general rows (`is_price_general = 1`) ticked for this install's city only, never `city_prices` (Sprint 2 Step 1, Question 1).
- The Russian copy is written only when the person confirmed its diff; a price mirrors only into a copy with the same number of rows, otherwise the result carries a warning.
- A Russian copy is created (`create-translation`) only of a Ukrainian post that has none, and linked to it in Polylang; what the payload does not translate is the source's, ACF values raw by field key, and its prices are always the source's.
- No URL literal of either install; the city comes from the site URL (root invariant 4). No secret in code: authentication is WordPress's own.

## Interfaces
- **MCP server** `https://{host}/wp-json/mcp/dovira` (Streamable HTTP, the adapter's sessions; the adapter's gate is `current_user_can( 'read' )`, so no valid application password = 401); `instructions` (the adapter has no instructions argument and sends the server description as `instructions`, so the text is `Server::INSTRUCTIONS`, the description; MCP tool names are the ability names with `/` → `-`, e.g. `dovira-describe-site`): it names every tool of the catalogue, in its order (`ServerTest` fails on a tool it does not name): call `describe-site` first; find with `list-posts` / `get-post` / `list-terms` / `list-media`; prices through `find-price-rows` → `update-price-row`, posts through `get-post` → `update-post` (only what changes); a new term (`create-term`) or image (`upload-media`) before `create-post`, in the status the person names; preview every write, show the diff, write only after consent, a changed request is a new preview; a price follows into the Russian copy by itself, a post's Russian copy only when the person agrees (`translation`); a post without a Russian copy gets one through `create-translation`, with the Russian texts the agent writes (what it leaves out stays Ukrainian); an image is uploaded with `upload-media` (a public URL, or base64) and then set in the post by id with `update-post` / `create-post`, two previewed writes; deleting is `trash-post`, administrators only, to the trash.
- **Abilities** (also REST `wp-abilities/v1/abilities/dovira/*` and `wp mcp-adapter serve --server=dovira`): read — `describe-site`, `list-posts`, `get-post`, `find-price-rows`, `list-terms`, `list-media`; write — `update-price-row`, `update-post`, `create-term`, `update-term`, `upload-media`, `create-post`, `create-translation`, `trash-post`. `Catalogue::TOOLS` lists them in this order, the order a chat uses them (reads first; a term or an image before the post that needs it, the Russian copy after the post, trashing last), and the server's `tools/list` follows it.
- **Read access:**
  - Content types (`service`, `employee`, `vacancy`, `page`, `post`) need the type's `edit_posts`, so editors and administrators.
  - Records (`conversation`, `application`, `questionary`) need `edit_others_conversations`, so administrators and the support role, never an editor. It is not `read_post`: core maps that to `read` for a published post.
  - `list-terms` needs the taxonomy's `assign_terms`; `list-media` needs `upload_files`; `find-price-rows` needs `service`'s `edit_posts`.
  - A missing id gets `dovira_post_not_found`; a type outside the scope is refused.
  - Every list is `{items, total, page, per_page}`, with `per_page` ≤ 50 (the schema refuses more, `ReadTools::paging()` clamps a direct call; `ReadAbilitiesTest` holds it for every list of the catalogue). `describe-site` lists at most 50 terms per taxonomy (with `terms_total`). `get-post` returns the whole post: no field is truncated and no length is reported (Sprint 2 Step 3, Question 1).
- **Result shapes:**
  - A post = `{id, type, status, lang, translations:{uk,ru}, title, slug, parent, link, menu_order, modified, terms:{taxonomy:[{id,name}]}, acf:{…by field name; repeater → [{…}], group → {…}, image → {id,url,alt}, file → {id,url,title}, post_object → {id,title}, relationship → [{id,title}]}, blocks:[…]}`.
    - `blocks` is the content of **every** type (blog posts, services and employees are built from `acf/*` blocks too). An `acf/*` block is `{block, fields}`, read by name through ACF's block meta. Any other block is `{block, html}`, its serialized markup. Freeform text is `core/freeform`. There is no `content_html`.
    - A `service`'s `acf.prices[].price` is the price in this install's city (`CityPrice`). It is the general price, or the row's `city_prices.price_city_{term}` for the install's `service-city` term, found by the slug of the URL's city. `null` means no price (the site shows the phone). `city_prices` is not shown.
    - Records and untranslated types have `lang: null` and `translations: {}`. Non-viewable types have `link: null`.
  - A `list-posts` item = `{id, type, status, lang, translations, title, modified, link}`.
  - A term = `{id, name, slug, parent, count, lang}`.
  - A media item = `{id, title, url, alt, mime, width, height, date}`.
  - `describe-site` = `{city, languages, user:{login, roles, can_delete}, post_types:[{name, label, hierarchical, translated, read_only, taxonomies, fields}], blocks:[{name, title, fields}], taxonomies:[{name, label, object_types, translated, read_only, terms (≤50), terms_total}]}`. A field there is `{name, label, type, required, choices?, sub_fields?}`, without `message`/`tab`/`accordion`.
  - A price row (`find-price-rows`: rows of the Ukrainian services whose `title` or `description` contains `text`, any case, as a paginated list) = `{service:{id,title}, row_index (from 0), title, description, price (this city's, `null` = none), per_city}`.
  - **Writes** (`WriteAbility`): the same call twice. Without `confirmation` = a preview `{diff:[{target:{id,lang}, field, from, to}], warnings:[…], confirmation}` and nothing written; an empty diff gives `confirmation: null`. With the token = a write `{written:[…ids], dump, warnings}`, where `dump` is the new file's name or `"existing"`. A token of another payload, user or session, used or older than 15 minutes = `dovira_confirmation_invalid`; a failed dump = `dovira_dump_failed`; both write nothing. Write abilities are annotated `readonly: false, destructive: true, idempotent: false`.
  - `update-price-row` = `{service_id, row_index, title?, description?, price? (> 0), confirmation?}`, permission `edit_post` of the service. `price` goes into the row's own column in this city (`price`, or `city_prices.price_city_{own term}`; a per-city row without that term = `dovira_city_term_missing`). It is changed in the Ukrainian copy only (`dovira_price_in_source` on a Russian one) and follows into the Russian copy's row of the same index; different row counts, or a copy the user cannot edit = a warning and Ukrainian only. `title` / `description` change the targeted copy only: the Russian text is a call on the Russian copy's id. The repeater is written whole through `update_field()`; `is_price_general`, `cities` and the other rows go back as read (ACF stores empty sub-fields of every row, as a save in wp-admin does).
  - `update-post` = `{id, title?, status?, slug?, parent?, menu_order?, terms?, acf?, blocks?, translation?: {id, …the same}, confirmation?}`, permission `edit_post` of every named post; only `service`, `employee`, `vacancy`, `page`, `post` (`dovira_read_only_type` for records). Only the named fields change (`PostWriter`):
    - `status` ∈ `publish|draft|pending|private` (`publish`/`private` need the type's `publish_posts`); `slug` is previewed as stored; `parent` only for hierarchical types; a trashed post is refused.
    - `terms` = `{taxonomy: [id | name]}`, the taxonomy's whole new set; existing terms only, a name looked up in the post's language, `service-city` by id; nothing is created.
    - `acf` = the post's own fields by name in the `get-post` shape, through `update_field()`; a repeater is replaced whole; `service.prices` is refused (`update-price-row`).
    - `blocks` = the whole new content in the `get-post` shape, within the blocks the editor allows on that post (`dovira_allowed_block_types()`: theme `acf/*`; core blocks too on `post`). An `acf/*` block's named fields replace those fields, the unnamed ones of the same block at the same index stay as stored; a new block gets every unnamed field's `default_value`, as the block editor stores them on insert (ACF applies a default only to a field the block data names, so `is_visible` would read empty); ACF flattens the data (`acf_setup_meta()` capture). A `{block, html}` must parse as exactly that block.
    - The translation is written only when named in `translation` (its id must be the post's Polylang translation); the preview lists both.
  - `create-post` = `{post_type, lang? (uk only), title, status, slug?, parent?, menu_order?, terms?, acf?, blocks?, confirmation?}`; `title` and `status` are required and the status has no default. Permission: the type's `create_posts`, plus `publish_posts` for `publish` / `private`.
    - `post` is created only where the install has a blog: the Ukrainian page `news` (`dovira_no_blog` otherwise, e.g. Kyiv).
    - The type's required ACF fields must be in `acf`; `dovira_required_fields` names the missing ones (`service.image`, `employee.photo`, `vacancy.description`).
    - The rest takes the update path's shapes and rules. A new term is created first with `create-term`.
    - A new service's `acf.prices` = rows `{title, description, price, linked_page?}`, written as general rows of this city.
    - The preview lists every value with `target.id: null` and `from: null`; the write is `{written:[new id], dump, warnings}`. The post is inserted, set to `uk` (`pll_set_post_language`), then its ACF fields and terms are written.
  - `create-translation` = `{id, title, status, slug?, parent?, menu_order?, terms?, acf?, blocks?, confirmation?}` (`Translator`): the Russian copy of the Ukrainian post `id`; `title` (Russian) and `status` are required, no default. Permission `edit_post` of the source and the type's `create_posts`, plus `publish_posts` for `publish` / `private`.
    - Refused: a source that is not `uk` (`dovira_not_source`, naming the Ukrainian id), one that already has a copy (`dovira_translation_exists`, naming it — change it with `update-post`), a record, a trashed or missing post; no Polylang = `dovira_polylang_missing`.
    - Carried from the source unless the payload names it: every ACF value raw by field key; the content verbatim (with `blocks`: planned like an `update-post` of the source's content — named fields replace, the rest stay raw); `category` / `post_tag` mapped to their `ru` terms (one without is left out, with a warning), `service-city` by id; the parent's `ru` translation (none = no parent, with a warning; a payload `parent` must be `ru`); `menu_order`; the page template; the featured image (types that support one: `page`, `post`); the date when the source has one. The slug is the payload's or the Russian title transliterated with Cyr2lat's Russian table.
    - `acf.prices` of a service = exactly the source's rows, `{title?, description?}` each; a `price`, if given, must be the source's in this city (`dovira_price_in_source`); another row count = `dovira_prices_invalid`. Prices, `is_price_general`, `cities`, `city_prices`, `linked_page` are the source's.
    - The preview lists every value of the copy with `target {id: null, lang: "ru"}`, `from: null` (prices in this city, every block of the result), and warns which text values stay Ukrainian. The write inserts as the connected user, `pll_set_post_language( ru )`, `pll_save_post_translations()` with the source's translations, the ACF fields, the terms: `{written:[copy id], dump, warnings}`.
  - `upload-media` = `{url | base64, filename?, alt?, title?, attach_to?, confirmation?}` (`MediaWriter`): exactly one of `url` / `base64` (`dovira_media_source_invalid`). Permission `upload_files`, plus `edit_post` of `attach_to` (a content post; records refused).
    - Accepted: a raster image whose type is one of the `image/*` types `get_allowed_mime_types()` allows the user, never SVG; at most `dovira_mcp_upload_max_bytes` (default 10 MB).
    - The preview downloads nothing. A `url` must be `http(s)` and pass `wp_http_validate_url()` (no local or private hosts: `dovira_media_url_invalid`); a HEAD request's `Content-Type` (or, without one, the URL's extension) must be an accepted type (`dovira_media_type_invalid`) and its `Content-Length` within the cap (`dovira_media_too_large`). `base64` (a `data:` prefix allowed) is judged by its length before decoding, then decoded strictly (`dovira_media_base64_invalid`) and typed by its bytes. Lines `source` (the URL, or `base64, N KB` — the bytes never go into the diff), `filename` (its extension follows the type), `title`, `alt`, `mime`, `attach_to {id, title}`, target `{id: null, lang: null}` (media are not translated).
    - The write downloads with `wp_safe_remote_get()` capped at the limit + 1 byte, checks the size and the type of the bytes again (`wp_get_image_mime()`), then `media_handle_sideload()` as the connected user, and writes `alt` as `_wp_attachment_image_alt`; the temp file is removed on every path. `{written:[id], dump, warnings, media:{id, url, alt, mime, width, height}}`; a failure adds nothing (`dovira_media_download_failed`, `dovira_media_upload_failed`).
    - `WriteAbility::run()` adds what a write returns besides `written` / `warnings` (here `media`) to the result; it never replaces `written`, `dump` or `warnings`.
  - `create-term` = `{taxonomy: category|post_tag, name, slug?, description?, parent? (category), confirmation?}`, permission the taxonomy's `manage_terms`; a name that exists in Ukrainian under that parent is refused with its id; the term is created in Ukrainian when Polylang translates the taxonomy (both are translated) and is not translated by the connector. `update-term` = `{id, name?, slug?, description?, parent?, confirmation?}`, permission `edit_terms`; a term of any other taxonomy (`service-city`) is refused. Both are writes `{written:[term id], dump, warnings}`.
  - `trash-post` = `{id, translation_id?, confirmation?}`, permission `manage_options` and `delete_post` of each named post; content types only, a post already in the trash refused. The preview is a `status → trash` line per post plus a warning naming a translation that stays; the write is `wp_trash_post()`, never `wp_delete_post()`. The translation is trashed only when named.
  - Errors of the post writes: `dovira_post_not_found`, `dovira_read_only_type`, `dovira_type_out_of_scope`, `dovira_not_a_translation`, `dovira_post_in_trash`, `dovira_status_invalid`, `dovira_cannot_publish`, `dovira_parent_invalid`, `dovira_taxonomy_invalid`, `dovira_term_unknown`, `dovira_term_language`, `dovira_unknown_field`, `dovira_prices_through_price_tool`, `dovira_block_not_allowed`, `dovira_block_markup_invalid`; of `create-translation` also `dovira_not_source`, `dovira_translation_exists`, `dovira_polylang_missing`, `dovira_prices_invalid`, `dovira_price_in_source`, `dovira_title_required`, `dovira_status_required`.
  - Changing these shapes = touches this feature's interface.
- **Filters/hooks:** `dovira_mcp_dump_retention_days`; `dovira_mcp_upload_max_bytes` (default 10 MB, at least 1); cron `dovira_mcp_dump_retention`.

## Roadmap
- Sprint 1 — Read everything and change a price from Claude: the connector is reachable from claude.ai on `dev.dovira.vet`, lists and shows every post type with structured ACF, blocks and translations, and changes a price row after a preview, with the session's dump taken first; existing posts are edited and trashed (administrators) under the same protocol (`sprints/SPRINT-1.md`)
- Sprint 2 — Create content: pages from blocks, blog posts, services, employees and vacancies with ACF; Russian copies linked through Polylang; images uploaded and attached; blog terms created and edited; the production checklist for both installs (`sprints/SPRINT-2.md`) — done 2026-11-05: both productions taken through `PRODUCTION-CHECKLIST.md`
