# Заповнення полів Yoast SEO (dovira.vet — Київ і Харків, Polylang)

## Файли

| Файл | Призначення |
|---|---|
| `dovira-seo-kyiv.json` | 35 сторінок × UA/RU з аркуша «Киев - структура» |
| `dovira-seo-kharkiv.json` | 35 сторінок × UA/RU з аркуша «Харьков - структура» |
| `dovira-seo-review.csv` | Обидва сайти в одній таблиці + довжини title/description — для вичитки |
| `yoast-import.php` | Скрипт імпорту, запускається лише через WP-CLI |

Інші аркуші (`Новые услуги`, `Страницы блога`, `Контент план`, `Семантика - блог`) не використовуються.

## Область завдання

Скрипт заповнює **тільки** поля Yoast:

- `_yoast_wpseo_title`
- `_yoast_wpseo_metadesc`
- `_yoast_wpseo_focuskw` — фраза з найвищою частотністю
- `_yoast_wpseo_focuskeywords` — решта фраз, лише якщо активний Yoast Premium (у безкоштовній версії одна ключова фраза на сторінку)

Слаги, URL, редиректи, H1 — **не чіпає**. H1 це контент сторінки, а не поле Yoast; колонка `h1` лишилась у JSON суто довідково.

## Пошук сторінок

Два кроки, без запасних варіантів:

1. **UA** — точний збіг URL з таблиці з реальним пермалінком. UA-адреси в таблиці правильні, тому вони й основа.
2. **RU** — `pll_get_post( $uk_id, 'ru' )`, тобто зв'язок перекладів Polylang.

RU-адреси з таблиці в пошуку **не використовуються взагалі** — вони лишились у JSON як довідка. Фактичні RU-слаги транслітеровані (`amputacziya` замість `amputation`), але для Polylang це не має значення: зв'язок перекладів живе в таксономії й від слага не залежить.

Головна сторінка обробляється окремо: `pll_get_post( get_option('page_on_front'), $lang )`, бо в Polylang вона своя для кожної мови.

Якщо крок не спрацював, скрипт нічого не вгадує, а пише в звіт:

- `NO UK PAGE` — UA-адреси з таблиці немає серед опублікованих сторінок
- `NO RU LINK` — UA-сторінка є, але до неї не прив'язано RU-переклад у Polylang

Обидва випадки — ручна робота в адмінці, скриптом їх лікувати не варто.

## Порядок виконання (окремо на кожному сайті)

### 0. Бекап

```bash
wp db export backup-before-yoast-$(date +%F).sql
```

### 1. Якщо щось не знайшлося — діагностика

```bash
wp eval-file yoast-import.php diagnose dovira-seo-kyiv.json
```

Бере кожен UA-URL, якого немає серед пермалінків, і шукає його слаг по **всіх** типах записів і **всіх** статусах напряму в `wp_posts`. У підсумку друкує, у якому `post_type` ці сторінки живуть, який у нього rewrite-слаг і чи він `public`.

Типові діагнози:

- `post_type "service": 33 hits, rewrite slug "services", public` — тип публічний, автовизначення підхопить його само
- те саме, але `NOT public` — тип зареєстровано з `'public' => false`, його треба дописати руками в `$dv_post_types` (рядок 46)
- `post_status "draft"` — сторінки не опубліковані
- `NO POST WITH SLUG` — слага немає взагалі, розбиратися в адмінці

### 2. Перевірка мапінгу

```bash
wp eval-file yoast-import.php resolve dovira-seo-kyiv.json
```

Нічого не пише. Формує `wp-content/uploads/yoast-import/kyiv-resolve.csv`: рядок таблиці, мова, метод, знайдений post ID, **фактичний заголовок сторінки на сайті** і її пермалінк.

Головна перевірка тут — звірити колонки `label_in_table` і `post_title`. Якщо навпроти «Ампутація» стоїть «Кастрація», значить зв'язок перекладів у Polylang прив'язаний не туди, і це треба лагодити до запису.

Мета: нуль `NO UK PAGE`, нуль `NO RU LINK`, нуль `LANG MISMATCH`.

### 3. Сухий прогін

```bash
wp eval-file yoast-import.php dry dovira-seo-kyiv.json
```

`<site>-<timestamp>-report.csv` зі статусами `WOULD-UPDATE` / `UNCHANGED` / `UNRESOLVED` / `DUPLICATE` і колонками old/new по кожному полю. `DUPLICATE` = два рядки резолвнулись в один пост, це помилка прив'язки перекладів.

### 4. Запис

```bash
wp eval-file yoast-import.php apply dovira-seo-kyiv.json
```

Додатково пише `<site>-<timestamp>-backup.csv` зі старими значеннями — точковий відкат без відновлення всієї БД.

### 5. Перевірка

```bash
wp eval-file yoast-import.php verify dovira-seo-kyiv.json
```

Звіряє і `postmeta`, і таблицю `wp_yoast_indexable`.

### 6. Якщо у вихідному коді сторінок досі старі сніпети

```bash
wp yoast index --reindex
```

Yoast з 14.0 тримає денормалізовану копію title/description у `wp_yoast_indexable`, і фронтенд читає саме звідти. <cite index="9-1">Yoast оновлює ці дані автоматично при збереженні контенту або метаданих</cite>, і скрипт додатково форсує перебудову індексабла після кожного запису — але якщо між версіями Yoast зміняться назви класів, виклик тихо впаде (побачиш warning). Тоді рятує CLI. <cite index="1-1">Команда працює на Yoast SEO 14.0+; прапорець `--reindex` видаляє всі наявні індексабли й будує їх наново.</cite>

## Технічні дрібниці

- Мапа пермалінків будується з `'lang' => ''` — <cite index="21-1">штатний параметр Polylang для кастомних запитів</cite>, порожній рядок означає всі мови.
- Типи записів визначаються автоматично: усі `public` типи, крім `attachment`. Раніше тут було жорстко `array('page','post')`, через що всі 33 сторінки послуг (вони в кастомному типі) не знаходились. Якщо тип зареєстровано як `'public' => false`, автовизначення його не побачить — дописуй руками в `$dv_post_types` (рядок 46).
- Якщо Polylang не активний, скрипт зупиняється одразу: без нього RU-сторінки знайти нічим.
- Константи замість змінних у конфігу — бо `wp eval-file` підключає файл усередині функції, і глобальних змінних там немає.

## Що варто виправити в таблиці до імпорту

Нічого не міняв автоматично — це тексти SEO-спеціаліста:

1. **Харків, головна RU і UA:** `Ветеринарная клиника в Харькове– Лечение…` / `Ветеринарна клініка у Харкові– Лікування…` — немає пробілу перед тире.
2. **Задовгі title:** 61 із 70 київських і 64 із 70 харківських рядків довші за 60 символів, максимум — 90. Google обріже.
3. **Description > 160:** Київ — головна RU (164). Харків — головна RU (167) і UA (162).
4. **Ключові фрази заповнені лише для 11 київських і 5 харківських рядків.** Решта піде без focus keyphrase — Yoast покаже «no focus keyphrase set». Це не помилка імпорту, в таблиці там порожньо.
